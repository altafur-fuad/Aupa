# Third-Party Integrations

## Integration principles

- Wrap each provider behind an interface/adapter so the core domain does not depend on provider-specific response shapes.
- Keep secrets server-side, use sandbox credentials before launch and separate test/live accounts.
- Add timeouts, bounded retries with backoff, circuit-breaker behavior where appropriate, idempotency, request IDs, provider status monitoring and reconciliation.
- Do not assume a provider callback arrives once or in order.

## 1. Payments

**Decision pending.** Select a Bangladesh-supported provider only after merchant onboarding, settlement terms, sandbox access, refund support and webhook documentation are verified. Candidate discussions may include SSLCOMMERZ, bKash/Nagad merchant payments or another supported gateway; this document does not assert eligibility or current integration support.

Required adapter contract:

```text
CreatePayment(orderId, amount, currency, idempotencyKey) -> provider reference + checkout action
VerifyWebhook(rawBody, headers) -> verified provider event
GetPaymentStatus(providerReference) -> canonical status
CreateRefund(paymentReference, amount, reason, idempotencyKey) -> refund reference/status
```

Rules:

- The server computes the amount and associates provider reference with a `payment_attempts` row.
- Store no PAN/CVV. Use provider-hosted or approved tokenized collection methods.
- Verify webhooks using current provider docs; dedupe event IDs; reconcile pending/unknown results.
- Payment `succeeded` must not be reversible by an ordinary callback; use a controlled refund/chargeback transition.
- Define COD vs online payment order transitions, charge timeout policy and customer messaging with the product owner.

## 2. SMS / email verification

Choose one vendor after testing coverage, delivery latency, cost, sender ID/template approvals and rate policies in target cities. A provider adapter should support `SendVerification`, `SendReset`, delivery result and safe retry. Avoid retrying a non-idempotent message send without a dedupe strategy. Keep content template-driven and localized. OTP values must never be logged.

## 3. Push notifications

For mobile push, evaluate Firebase Cloud Messaging and Apple Push Notification service through a maintained client/provider interface. Store device tokens with account/device relation, support token rotation, and delete stale tokens. Push notifications are best-effort; they never replace persisted order state. Do not include full address, access token or sensitive payment details in push content.

## 4. Maps/geocoding/routing

Provider choice depends on coverage, pricing, license and data retention. Store canonical address text and optional coordinates; validate delivery zones separately from straight-line distance. Use rate limits, cache geocoding results appropriately and prevent SSRF by accepting only provider-defined inputs rather than arbitrary fetch URLs. Provide manual address selection fallback when maps fail.

## 5. File/image storage

Use Supabase Storage or a compatible object store for restaurant/menu images. Public catalog images can be served via controlled public buckets/CDN; private documents need private storage and short-lived signed URLs. Enforce file type/size limits, image decoding/transcoding, safe names and upload authorization. Do not trust file extension or fetch arbitrary customer-supplied URLs server-side.

## 6. Analytics/crash reporting

Pick an analytics/crash tool that supports privacy controls and regional/legal requirements. Do not send auth tokens, OTPs, card data, full phone/email, address text or raw request bodies. Use pseudonymous IDs where needed, disclose analytics in privacy policy and define retention/opt-out where appropriate.

## 7. Integration reliability checklist

- Sandbox success/failure/timeout test cases.
- Signature verification and webhook replay tests.
- Duplicate event/request behavior documented.
- Secret rotation and provider credential expiry alerts.
- Reconciliation job for stuck `pending`/`unknown` payments.
- Timeouts and retry budget; avoid retry storms.
- Runbook for provider outage and customer communication.
- Contract tests against provider fixtures, while keeping a small periodic live sandbox smoke test.
