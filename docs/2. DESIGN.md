# Product & Technical Design

## 1. Experience principles

- Keep ordering quick: search/browse → restaurant/menu → cart → address/payment → confirmation → tracking.
- Show availability, delivery estimate, price, delivery fee, taxes/discounts and cancellation rules before confirmation.
- Every screen must model loading, success, empty, offline, validation and server-error states.
- Never imply payment succeeded based only on an app redirect. Show “Payment processing” until server-confirmed.
- Use localization-ready strings; avoid hard-coded Bangla/English text inside widgets.

## 2. Customer information architecture

1. **Auth:** onboarding, phone/email verification, login, forgot password, reset password.
2. **Home:** service-area selector/address, search, categories, featured restaurants and recent orders.
3. **Restaurant:** rating/estimated time, menu categories, item details/options, availability.
4. **Cart:** quantities, item notes, subtotal, discount, fee, tax, total; server recalculates at checkout.
5. **Checkout:** address, delivery instructions, payment method, fees, policy consent and place-order button.
6. **Order details:** order timeline, merchant/rider status, permitted rider location, call/support shortcuts.
7. **Orders:** active/history, reorder with fresh availability/price validation.
8. **Profile:** personal details, addresses, notifications, privacy, sessions/logout, support.

## 3. Merchant, rider and admin surfaces

- **Merchant:** incoming orders, accept/reject with reason, estimated prep time, mark preparing/ready, catalog/menu management, operating hours and temporary pause.
- **Rider:** availability, assigned job, pickup verification, navigation handoff, delivery confirmation (OTP/PIN/photo policy to decide), job history. Location is collected only when required and disclosed.
- **Admin/support:** role-based queues, account/restaurant/rider review, order timeline, payment reconciliation, refunds, abuse reports, configuration and immutable audit trail. Avoid giving all operators unrestricted database access.

## 4. Flutter architecture

Use feature-first structure with UI and data layers as the default; introduce domain/use-case classes for checkout, pricing display, state transitions or other complex flows. Flutter's architecture guide recommends separation between Views, ViewModels, Repositories and Services; adapt rather than treating it as a rigid rule: https://docs.flutter.dev/app-architecture/guide

Suggested structure:

```text
lib/
  app/                 # router, theme, localization, app bootstrap
  core/
    api/               # HTTP client, auth interceptor, error mapping
    secure_storage/    # platform secure token storage abstraction
    config/            # non-secret public configuration
    widgets/           # shared components
  features/
    auth/{data,domain,presentation}/
    restaurants/{data,domain,presentation}/
    menu/{data,domain,presentation}/
    cart/{data,domain,presentation}/
    checkout/{data,domain,presentation}/
    orders/{data,domain,presentation}/
    tracking/{data,domain,presentation}/
    profile/{data,domain,presentation}/
```

Suggested per-feature responsibilities:

- `View`: render state and forward user actions; no HTTP or business policy.
- `ViewModel`/state controller: loading/error/data state; use cases where behavior merits it.
- `Repository`: domain-shaped interface and cache/source-of-truth coordination.
- `ApiService`: HTTP only; no widget dependencies.
- DTOs: serialization; map into domain models so API schema changes do not cascade through widgets.

Choose one state-management/router stack and standardize it early. Example defaults: Riverpod for state, `go_router` for route/deep-link handling, an HTTP client such as Dio, and `flutter_secure_storage` for tokens. These are suggestions, not forced dependencies; verify current compatibility and platform limitations before pinning versions.

## 5. UI states and interaction rules

- Disable the submit button while one request is in flight, but still rely on server idempotency.
- Keep cart contents locally for UX, but validate prices, restaurant relationship, availability and promotions server-side.
- If a refresh token is rejected, clear private state and return to login. Do not loop refresh indefinitely.
- Cache public restaurant/menu data with an expiry; do not cache sensitive order details indefinitely.
- For tracking, reconnect/resume safely; show last update time and fallback to periodic polling.

## 6. API and design conventions

- Base path `/v1`; JSON camelCase; ISO-8601 UTC timestamps; UUIDs; monetary amounts represented as integer minor units (BDT poisha) or explicit decimal values, never binary floating-point.
- Use stable error codes and human-readable localized messages on the client.
- Pagination uses `limit` plus opaque `cursor` where practical.
- Every mutation must have server authorization. Hiding buttons in Flutter is not access control.

## 7. Visual system checklist

Define typography scale, spacing tokens, semantic colors, button/input variants, empty/error/loading components, image placeholders, modal behavior and motion guidelines. Test small Android screens, large text, keyboard overlap, slow internet, dark mode (if supported), and Bangla glyph rendering.

## 8. UX research still required

Validate the design with 5–8 target users and at least one merchant/rider. Observe users completing first order, changing address, dealing with unavailable items, cancelling and understanding a pending payment. Fix repeated confusion before expanding scope.
