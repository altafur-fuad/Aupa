# HTTP API Contract

**Base URL:** environment-specific, e.g. `https://api.example.com/v1`  
**Transport:** HTTPS only. JSON request/response. Timestamps are ISO-8601 UTC. IDs are UUID strings. Monetary values use integer minor units (`amountPoisha`) and `currency: "BDT"`.

## 1. Standard headers

- Protected calls: `Authorization: Bearer <access_token>`.
- Mutating checkout/payment operations: `Idempotency-Key: <client-generated high-entropy key>`.
- Optional: `X-Request-Id` for support correlation; server validates or replaces it with a safe generated ID.
- `Content-Type: application/json`.

## 2. Success and error envelope

Success response shape is resource-specific, for example:

```json
{
  "data": { "id": "uuid", "status": "placed" },
  "meta": { "requestId": "req_..." }
}
```

Error shape:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Please check the submitted fields.",
    "fields": [{ "name": "phone", "code": "INVALID_FORMAT" }]
  },
  "meta": { "requestId": "req_..." }
}
```

Never return SQL details, stack traces, provider secrets or whether a specific account exists where that enables enumeration. Localize display messages in Flutter using stable error codes.

## 3. HTTP status rules

- `200` read/update success; `201` created; `202` accepted for asynchronous processing; `204` successful no-content action.
- `400` malformed request; `401` missing/invalid/expired authentication; `403` authenticated but not allowed; use `404` where hiding resource existence is appropriate.
- `409` state conflict or incompatible idempotency reuse; `422` semantic validation where chosen; `429` rate limited; `500` unexpected error; `503` temporary dependency outage.

## 4. Endpoint inventory

### Auth

| Method & path | Purpose |
|---|---|
| `POST /auth/register` | Create account; return verification-required state, not a privileged session if contact must be verified. |
| `POST /auth/login` | Verify credentials, return short-lived access token and refresh token/session result. |
| `POST /auth/refresh` | Rotate refresh token; reject reused/revoked family. |
| `POST /auth/logout` | Revoke current session/refresh token. |
| `POST /auth/logout-all` | Revoke all user sessions after re-authentication as needed. |
| `POST /auth/verify-contact` | Submit one-time verification code/link token. |
| `POST /auth/verification/resend` | Resend within account/IP/contact rate limits. |
| `POST /auth/password/forgot` | Always return generic success text whether account exists or not. |
| `POST /auth/password/reset` | Consume single-use reset token and update password. |
| `GET /me` | Current identity and permitted profile. |
| `PATCH /me` | Update allowlisted profile fields. |

### Customer/catalog

| Method & path | Purpose |
|---|---|
| `GET /restaurants?zoneId=&q=&cursor=&limit=` | Search/list open or active restaurants for a service zone. |
| `GET /restaurants/{id}` | Restaurant details. |
| `GET /restaurants/{id}/menu` | Categories/items and current availability. |
| `GET /addresses` / `POST /addresses` | List/create own addresses. |
| `PATCH /addresses/{id}` / `DELETE /addresses/{id}` | Update/delete own address only. |
| `POST /checkout/quote` | Recalculate items, fees, discounts and serviceability; quote may expire. |
| `POST /orders` | Create order using current cart lines and quote reference; requires idempotency key. |
| `GET /orders?cursor=&limit=` | Current user's order history. |
| `GET /orders/{id}` | Get own order with permitted timeline details. |
| `POST /orders/{id}/cancel` | Cancel only under current policy/state; idempotent. |
| `POST /orders/{id}/payment-attempts` | Create/reuse a payment attempt server-side. |
| `GET /orders/{id}/tracking` | Permitted delivery status and freshness metadata. |

### Merchant/rider/admin (role + scope required)

- `GET /merchant/orders?status=&cursor=`
- `POST /merchant/orders/{id}/accept`, `/reject`, `/preparing`, `/ready`
- `GET /rider/jobs`, `POST /rider/jobs/{id}/accept`, `/pickup`, `/delivered`
- `POST /rider/location` (rate-limited, only for an active assigned job)
- `GET /admin/orders`, `POST /admin/orders/{id}/refunds`, `PATCH /admin/restaurants/{id}/status`
- `GET /admin/audit-logs` (strongly restricted)

Avoid generic endpoints like `PATCH /orders/{id}` where callers can submit arbitrary `status`, `paymentStatus`, `total` or `role` fields.

### Provider webhook

- `POST /webhooks/payments/{provider}` — provider signature verification, provider event de-duplication, body size limit and no user bearer token required. Authenticate using the provider's documented webhook mechanism.

## 5. Example: order creation

Request:

```http
POST /v1/orders HTTP/1.1
Authorization: Bearer <access_token>
Idempotency-Key: 7ef3...random...
Content-Type: application/json
```

```json
{
  "restaurantId": "0c1...uuid",
  "addressId": "d92...uuid",
  "items": [
    { "menuItemId": "b77...uuid", "quantity": 2, "optionValueIds": [], "note": "No onion" }
  ],
  "paymentMethod": "cod",
  "quoteId": "quote_..."
}
```

The server must reload current menu prices/availability, verify every item belongs to the restaurant, validate address ownership/serviceability, re-evaluate quote and promotion eligibility, calculate all totals and persist order + items + outbox event in one DB transaction. The client must not submit authoritative unit prices/totals.

Response:

```json
{
  "data": {
    "id": "order-uuid",
    "orderNumber": "FD-2026-000123",
    "status": "placed",
    "paymentStatus": "not_required",
    "currency": "BDT",
    "amounts": {
      "subtotalPoisha": 48000,
      "deliveryFeePoisha": 5000,
      "discountPoisha": 0,
      "taxPoisha": 0,
      "totalPoisha": 53000
    }
  },
  "meta": { "requestId": "req_123" }
}
```

Example amounts are illustrative, not a pricing rule.

## 6. Idempotency contract

- Scope key by authenticated principal + operation. Persist key, request fingerprint and result/aggregate ID with a unique constraint.
- Same key + same normalized request returns the same outcome. Same key + different request returns `409 IDEMPOTENCY_KEY_REUSED`.
- Keep the record for at least the order/payment retry and reconciliation window; define retention explicitly.
- For provider calls, reuse provider idempotency keys when supported. A timeout is an unknown result until reconciled; do not blindly create a second charge.

## 7. Auth token contract

- Access token short-lived (starting target 10–15 minutes), signed using an asymmetric key where feasible, with `iss`, `aud`, `sub`, `iat`, `exp`, `jti` and `kid`.
- Validate algorithm allowlist, signature, issuer, audience, expiration and not-before; do not trust roles/scopes beyond verified server-managed claims and current authorization policy.
- Refresh token is opaque and high entropy, stored hashed server-side and rotated on use. Keep raw refresh token only in platform secure storage; never log it.

## 8. Pagination and sorting

Use allowlisted sort keys only. Cursor pagination should encode a stable ordering such as `(created_at, id)` and must be bound to the caller's query scope. Never concatenate user input into SQL identifiers or order-by strings.

## 9. API schema governance

Maintain OpenAPI in `api/openapi.yaml`; validate examples in CI and generate Dart models/client code only if it improves consistency. Changes should be additive where possible. Breaking changes require a versioning/deprecation plan.
