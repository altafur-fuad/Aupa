# Debugging and Operations Runbook

## 1. First principles

- Start with impact and timeline; identify whether issue is app, API, database, provider or worker.
- Use `requestId`, order ID and provider reference to correlate events. Do not copy bearer tokens, passwords, OTPs, full customer addresses or payment credentials into tickets.
- Prefer safe read-only diagnosis before changing data. Never “fix” order/payment state with arbitrary SQL during an incident.
- Check whether retries are safe before replaying a mutation.

## 2. Minimum telemetry

For Go API and Rust worker, capture structured fields: timestamp, level, service/version, environment, request/trace ID, route/template (not raw sensitive path params), status code, duration, error code, DB pool metrics and provider result category. Redact `Authorization`, cookies, token/code fields, secrets and unnecessary PII.

Dashboards/alerts:

- API request rate, p95 latency, 5xx, 401/403/429 rates.
- DB pool in-use/wait time, connection errors, slow queries and transaction/deadlock failures.
- Login/OTP abuse and refresh-token reuse events.
- Orders stuck in `pending_payment`, unaccepted too long, or assigned without progress.
- Payment webhook verification failures, duplicate event count, reconciliation backlog and refund mismatch.
- Outbox oldest pending age, attempts/dead-letter count and Rust dispatch worker heartbeat.

## 3. Common failure playbooks

### Flutter gets 401 repeatedly

1. Inspect request ID and token expiry metadata without printing the token.
2. Verify app refresh logic is single-flight; multiple simultaneous 401s must not rotate the same refresh token in parallel.
3. Check clock, issuer/audience/key rotation and backend version skew.
4. If refresh fails, clear private cached data and send user to login; avoid infinite retries.

### Login/OTP failures

1. Check provider status, account/contact rate limit and challenge expiry/attempt limit.
2. Use local/staging test provider to verify end-to-end; never print the actual OTP in production logs.
3. Look for duplicate contact races/unique constraint responses.
4. Check the provider's message status and configuration; do not reveal account existence to caller.

### Cannot connect to Supabase Postgres

1. Verify the connection string from the dashboard's Connect panel; do not compose pooler host/username manually.
2. Check direct connection network/IP version; for IPv4-only environments choose the supported pooler mode.
3. Validate database password URL-encoding, TLS mode and secret injection.
4. Check pool sizing and open connections; reuse a DB pool per process.
5. For transaction poolers, review driver compatibility and session/prepared-statement limitations.

Official reference: https://supabase.com/docs/guides/database/connecting-to-postgres

### Duplicate order/payment concern

1. Stop unsafe manual retries; inspect idempotency key, request fingerprint, order and payment-attempt rows.
2. Query provider canonical status using provider reference.
3. Check deduped webhook rows and `order_events` sequence.
4. Reconcile through supported application job/admin workflow; do not delete audit evidence.
5. Add regression test if caused by code.

### Order stuck after payment

1. Distinguish payment state from order fulfillment state.
2. Check webhook signature errors, provider event ID, event processing state and outbox backlog.
3. Query provider status server-to-server if the result is unknown.
4. Re-run idempotent reconciliation only after verifying the provider/event semantics.
5. Notify support if customer-visible state is delayed; never mark payment successful merely to clear the queue.

### Rust dispatch worker stopped

1. Check process health, database access and last successful job.
2. Inspect lease expiries, attempt count and dead-letter events.
3. Restart worker only after verifying safe retry semantics.
4. Keep manual assignment fallback; ensure Go revalidates proposed rider/order state before commit.

### High database connections/latency

1. Check per-process pool size × replica count and leaked/long transactions.
2. Inspect slow queries/index usage and transaction lock waits.
3. Scale only after measuring; reducing pool sizes or switching connection mode may be safer than increasing DB load.
4. Ensure no payment/network call runs inside an open DB transaction.

## 4. Incident severity and response

- **SEV-1:** suspected customer/payment data exposure, duplicate/uncontrolled charges, widespread checkout failure, database corruption. Page owner, protect evidence, restrict unsafe endpoints if necessary, notify leadership/provider and follow legal/contract notification obligations.
- **SEV-2:** substantial order placement/dispatch degradation or payment confirmation delays with workaround. Assign incident lead, communicate updates and track mitigation.
- **SEV-3:** isolated UX/integration defect with safe workaround. Log, prioritize and monitor.

During incident: record timeline, scope, customer impact and changes; avoid deleting events/logs. After resolution: document root cause, contributing factors, detection gaps and measurable follow-up actions.

## 5. Safe operational commands

Keep a repository `make`/task script for health checks and read-only diagnostics. Destructive DB maintenance and production state correction require peer review, backup/restore awareness, a ticket and explicit approval. Never paste production connection strings into terminals/screenshots shared publicly.

## 6. Recovery readiness

- Know who owns Supabase billing/support and how to view current plan backup/PITR settings.
- Maintain and protect a copy of migration history and required configuration.
- Rehearse restore to a separate project and application smoke test.
- Document DNS/API rollback, key rotation, payment-provider outage response and user-session revocation.
- Define recovery time and recovery point objectives based on business need; don't claim a recovery guarantee that has not been tested.
