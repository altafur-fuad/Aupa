# Authentication & Security

> Custom authentication replaces Supabase Auth only if the team assumes responsibility for the full identity lifecycle. Use established, maintained crypto/JWT libraries; do not invent cryptographic primitives.

## 1. Preferred MVP model

Flutter → Go Auth/API → Supabase PostgreSQL. Supabase Auth is not used. The mobile app does not connect directly to the database or use the Supabase secret/service-role key. Go authenticates all protected API calls and enforces object-level authorization. The Rust worker receives trusted internal work and has no public login surface.

## 2. Registration/login

1. Normalize email/phone; validate length and format.
2. Create account in `pending_verification` if contact verification is required. A unique DB constraint protects duplicate contacts under race conditions.
3. Password hashing uses Argon2id with parameters meeting or exceeding current OWASP guidance and benchmarked against the target instance; store encoded hash including parameters/salt. See https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html
4. On login, compare the supplied password using the library and use a generic response that does not reveal whether the user exists. Add IP + account/contact rate limits, progressive delays and abuse monitoring. Avoid irreversible account lockout as a simple DoS vector.
5. After verification and successful authentication, issue short-lived access token and a refresh token bound to a server-side session.

## 3. Token/session design

- **Access token:** signed JWT, initial target 10–15 minutes. Claims: `iss`, `aud`, `sub` (user UUID), `iat`, `exp`, `jti`, `kid`; add minimal scopes/roles only if needed and keep them short-lived. Never place secrets or PII in JWT claims.
- **Algorithm:** asymmetric signature such as EdDSA/ES256/RS256 supported by maintained libraries; configure a strict allowlist. Keep private signing key server-side, public verification key on Go/Rust services. Support key rotation via `kid` and an overlap period.
- **Refresh token:** opaque random value generated by a CSPRNG (at least 256 bits of entropy is a conservative target), stored as a cryptographic hash in `auth_sessions`; rotate on every use. A JWT refresh token is not required and often makes revocation harder.
- **Refresh reuse:** if an already-rotated token is presented, revoke the token family/session set and log a security event. Handle simultaneous refresh requests carefully so the app does not trigger false reuse alarms; serialize refresh in the Flutter client.
- **Logout:** revoke current refresh token/session; access JWT remains usable until short expiry unless an online revocation/denylist is checked. For sensitive operations, check account/session status or require re-authentication.
- **Token storage:** use iOS Keychain/Android Keystore-backed secure storage through a maintained Flutter package. Keep access token in memory where possible; if persistence is necessary, secure it. Never put tokens in URLs, logs, crash reports or ordinary preferences. Web deployments should reassess cookie/BFF architecture; do not store tokens in browser localStorage.

OWASP session-management guidance: https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html

## 4. Contact verification and password recovery

- Choose phone OTP, email verification link/code, or both after selecting an SMS/email provider.
- Generate high-entropy random challenge; store only a hash, purpose, contact, expiry, consumed timestamp, attempt count and creation rate metadata. OTPs are low entropy by design, so compensate with short expiry, strict attempt limits, cooldowns and rate limits.
- Never log or store OTP plaintext. In local development use a fake/test provider, never deliver real messages accidentally.
- Password reset endpoint returns the same public response whether account exists. Reset token is random, hashed at rest, single-use, short-lived and invalidated after password change. Revoke existing sessions after reset or ask the user to choose the policy.
- Do not send passwords or reset tokens by support chat; support staff must not be able to view passwords or OTPs.

## 5. Authorization

- Authenticate first, then authorize action + object + scope. Every `/orders/{id}`, `/addresses/{id}`, merchant, rider and admin operation checks relationship in trusted server code.
- Roles belong in `user_roles`; merchant staff access must be bound to a specific restaurant. Rider access must be bound to assigned jobs. Customer order access must match `customer_id`.
- Deny by default. Unknown client fields are rejected/ignored through explicit DTO allowlists; never bind incoming JSON directly to privileged DB models.
- Admin and refund tools need least privilege, audit trail, stronger authentication/MFA where feasible and explicit support role scopes.

## 6. Supabase JWT/RLS reality check

Supabase's `auth.uid()` is derived from the auth context/JWT claims Supabase recognizes; a token signed by our Go service will not magically produce a valid user identity in RLS. Supabase documents configured custom/third-party JWT support: https://supabase.com/docs/guides/auth/jwts

**MVP:** clients cannot call Supabase Data API directly. Backend services connect with server-side credentials and enforce authorization themselves. Create restricted DB roles and grants; remember a privileged/secret key or role may bypass RLS. Never ship secret/service keys in Flutter. Apply RLS to exposed tables as defense in depth, but know which connection role is used in every request.

If adopting direct client-to-Data-API access later, first configure and verify supported JWT trust, signing keys/claims, role mapping and `auth.uid()` in integration tests. Then enable RLS policies for every exposed table. Test cross-user/cross-merchant access denial. Relevant docs: https://supabase.com/docs/guides/database/postgres/row-level-security

## 7. API and infrastructure controls

- HTTPS only; secure TLS configuration; no production cleartext.
- Strict request size limits, content types, deadlines, input schema validation and safe error messages.
- Rate limit login, OTP requests/verification, reset, searches, checkout, rider location and webhook endpoints.
- CORS allowlist only if browser-based client exists; CORS is not authorization.
- Parameterized SQL; no interpolated client input in SQL values/order-by/table names.
- Restrict database network access where possible; TLS DB connections, small connection pools and least-privileged credentials per service.
- Secret manager/environment injection; rotate secrets, keep development and production keys separate.
- Dependency scanning, container scanning, SBOM if practical, patch process and security contact.
- Redact password, `Authorization`, refresh tokens, OTPs, full provider payloads and sensitive personal fields from logs.

OWASP REST/API security: https://cheatsheetseries.owasp.org/cheatsheets/REST_Security_Cheat_Sheet.html and https://owasp.org/www-project-api-security/

## 8. Webhook security

- Verify provider signatures over the exact documented payload/raw body; enforce timestamp window when provider supports it.
- Treat webhook as external input; dedupe `(provider, provider_event_id)`; allowlist event types; fetch canonical transaction status if needed.
- Store only limited raw content when required for disputes, with access and retention restrictions.
- Do not trust event order; apply valid state transition and reconcile uncertain payment states.
- Webhook endpoint should not require customer JWT. Authenticate using provider's mechanism and rate-limit safely.

## 9. Threat model checklist

| Threat | Control |
|---|---|
| Credential stuffing | adaptive password hash, rate limits, generic errors, abuse alerts, optional MFA. |
| Token theft | secure storage, short access TTL, refresh rotation/revocation, no logs, key rotation. |
| Broken object authorization | actor-resource relationship checked in every handler; negative tests. |
| Fake price/discount | server calculates totals from current DB state. |
| Duplicate orders/charges | API idempotency + provider idempotency + reconciliation. |
| Forged payment webhook | signature verification, event dedupe and canonical verification. |
| SQL injection | parameterized SQL, least-privileged roles, input validation. |
| RLS misconception | explicit connection-model diagram, integration tests, no public DB credentials. |
| Insider/admin misuse | scoped roles, re-auth/MFA, audits, alerting and separation of duties. |
| Location privacy breach | active-job-only updates, authorization, short retention and minimal precision. |

## 10. Release gates

Before public launch: independent review of auth/token lifecycle; automated test of role/object access matrix; expired/reused refresh tests; recovery abuse tests; secrets scan; TLS check; webhook replay tests; dependency scan; backup restore; privacy notice and retention policy; incident/revocation runbook.
