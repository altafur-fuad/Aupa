# MCP Connection (Optional Developer Integration)

## Purpose

Model Context Protocol (MCP) is an optional protocol for connecting AI/developer tools to approved resources and actions. It is **not** a runtime dependency for the food delivery customer app, order pipeline, payment processing or rider dispatch. The app must continue to operate normally when every MCP server is offline.

Specification reference: https://modelcontextprotocol.io/specification/2025-11-25

## Safe use cases

- Local development assistant reads non-secret API docs and migration files.
- Read-only test tool retrieves sanitized staging logs/metrics.
- A support assistant searches internal documentation and prepares (but does not execute) a response.
- A controlled tool proposes a test restaurant/menu seed or summarizes test results.

## Disallowed by default

- Production SQL shell or unrestricted table access.
- Reading `.env`, private signing keys, database URLs, payment keys or raw customer data.
- Direct refund, role changes, production deployment, order status override, real OTP/SMS send or destructive migration without explicit human approval and narrow capability-specific authorization.
- Exposing private tools to the internet without authentication, authorization, transport protection and an owner.

## Suggested optional topology

```text
Developer-approved MCP client
          |
     local/private MCP server
          |
 allowlisted tools only -> local/dev services or sanitized staging read APIs
```

Begin with local stdio transport for developer workflows where feasible. For remote MCP servers, use the current specification's authorization and transport guidance; authenticate each request, scope access to the user and avoid passing bearer tokens through to downstream services without a deliberate security design. Never assume that an MCP connection is trusted simply because it was initiated by an AI tool.

## Tool policy

- Use named allowlisted functions, not arbitrary SQL or shell by default.
- Every tool has input schema, permission scope, timeout, audit log and error redaction.
- Read-only tools are preferred; destructive operations require explicit user confirmation and a human review path.
- Separate dev/staging/prod servers and credentials; do not reuse a personal admin token for agents.
- Return only minimum necessary data; mask phone/email and exclude sensitive payment data.
- Prevent prompt injection from issue text, logs or database fields from becoming executable instructions. Tool output is data, not authority.

## Example initial tool catalogue

| Tool | Access | Guardrails |
|---|---|---|
| `docs.search` | Read-only docs | Excludes `.env`, secrets and private customer docs. |
| `tests.run` | Local command allowlist | No arbitrary shell; time/output limits. |
| `staging.metrics` | Read-only staging | Aggregate metrics only. |
| `staging.order_lookup` | Read-only, sanitized | Requires request ID/test order; hides contact info. |
| `migration.review` | Static SQL analysis | Does not apply migrations. |
| `production.deploy` | Disabled by default | If ever enabled, human approval, protected CI and audit. |
| `payment.refund` | Disabled for agents | Refund must use an authenticated human workflow. |

## Implementation plan

1. Do not add MCP to the MVP release dependency graph.
2. Define the precise developer workflow and data scope first.
3. Start with documentation and test-result tools on local/staging data.
4. Add auth and audit policies, threat review and tool-level tests before remote exposure.
5. Pin compatible MCP SDK/spec versions and monitor official changelog: https://modelcontextprotocol.io/specification/draft/changelog

## Acceptance criteria

App checkout works with MCP stopped. No tool can access production secrets by default. Every tool is scoped, authenticated where remote, logged without secrets, and tested against malicious tool input and prompt-injection attempts.
