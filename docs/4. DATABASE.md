# Database Design — Supabase PostgreSQL

## 1. Conventions

- PostgreSQL on Supabase is the source of truth. Use SQL migrations in Git, not undocumented dashboard-only changes.
- UUID primary keys; `timestamptz` in UTC; `numeric` or integer minor units for money; explicit currency (`BDT`). Use integer poisha for BDT amounts and document conversions.
- Store user-provided addresses as snapshots on orders so later profile edits do not change prior orders.
- Add `created_at`, `updated_at` as appropriate, foreign keys, check constraints, unique constraints and indexes. Avoid soft-delete everywhere by default; define lifecycle per entity.
- Prefer normalized operational tables. Keep order-time copies of product name, unit price, selected options and relevant fee/tax details in `order_items`/order snapshots.

## 2. Proposed tables

The schema below is the logical MVP set. Prefixes are shown as logical groupings; using PostgreSQL schemas (`identity`, `catalog`, `commerce`, `payments`, `ops`) is recommended if your migration/permission workflow supports it. A simpler `public` schema is acceptable for the first iteration if the logical ownership is documented.

### Identity

- `users`: `id uuid PK`, `display_name`, normalized `email` nullable, normalized `phone` nullable, `password_hash` nullable, `email_verified_at`, `phone_verified_at`, `status`, `created_at`, `updated_at`. Unique partial indexes on normalized email/phone when not null. Do not store OTP plaintext.
- `user_roles`: `user_id FK`, `role` enum/check (`customer`, `merchant`, `rider`, `support`, `admin`), optional `scope_id` for restaurant/organization; unique composite index. A user may have more than one scoped role; never trust role sent by the client.
- `auth_sessions`: `id uuid PK`, `user_id FK`, `refresh_token_hash`, `token_family_id`, `expires_at`, `rotated_at`, `revoked_at`, `created_at`, `last_used_at`, `device_label` optional. Store a hash of opaque refresh tokens, not the raw token.
- `verification_challenges`: `id`, `user_id/contact`, purpose, `code_hash`, `expires_at`, `attempt_count`, `consumed_at`, `created_at`; throttle by account/contact and IP. Delete/archive safely after expiry.
- `password_reset_tokens`: opaque token hash, user ID, expiry, consumed timestamp; one-time only.

### Customer and catalog

- `addresses`: `id`, `user_id`, label, address lines, area/zone, optional lat/lng, delivery instructions, `is_default`, timestamps.
- `restaurants`: `id`, name, slug, description, phone, address, zone, lat/lng, status (`draft`, `active`, `paused`, `suspended`), opening-hours JSON or normalized schedule, service/commission config, timestamps.
- `restaurant_members`: `restaurant_id`, `user_id`, staff role; unique pair.
- `menu_categories`: `id`, `restaurant_id`, name, display order, active.
- `menu_items`: `id`, `restaurant_id`, `category_id`, name, description, current price in poisha, image URL, availability, preparation estimate, timestamps.
- `menu_item_options` / `menu_option_values`: optional item variants/add-ons with explicit price delta and constraints. Only add if UI needs options.
- `promotions`: optional MVP-later table with time window, usage limits, funding party and server-side eligibility rules. Do not accept a client-calculated discount.

### Commerce

- `orders`: `id`, human-readable `order_number` unique, `customer_id`, `restaurant_id`, status, payment status, fulfillment status, currency, subtotal, discount, tax, delivery_fee, service_fee, total, address snapshot JSON, customer note, cancel reason, `idempotency_key`, `created_at`, `updated_at`, `accepted_at`, `delivered_at`. Unique `(customer_id, idempotency_key)` where key is not null.
- `order_items`: `id`, `order_id`, `menu_item_id` nullable if catalog item later removed, name snapshot, unit price, quantity, options snapshot, line total, customer note. Check quantity > 0 and amounts >= 0.
- `order_events`: `id`, `order_id`, actor type/ID, from_status, to_status, event type, reason, metadata with an allowlisted shape, timestamp. Append-only for normal application roles.
- `carts`/`cart_items`: optional server-side carts; a local client cart is okay, but checkout must revalidate everything. If using database carts, constrain one active cart per customer/restaurant as product rules require.

### Payments and operations

- `payment_attempts`: `id`, `order_id`, provider, provider reference, amount, currency, status (`created`, `pending`, `succeeded`, `failed`, `cancelled`, `unknown`, `refunded`), idempotency key, timestamps. Unique provider reference when present.
- `payment_webhook_events`: provider, provider event ID, payload hash, received/processed timestamps, processing status; unique `(provider, provider_event_id)`. Store minimal/redacted metadata unless payload retention is required.
- `refunds`: `id`, payment/order IDs, amount, reason, requested/processed by, provider refund reference, status, timestamps.
- `riders`: `id`, user ID unique, vehicle/details needed, status, service zone.
- `delivery_jobs`: `id`, order ID unique, rider ID nullable, status, pickup/delivery timestamps, assignment algorithm version, assignment metadata, timestamps.
- `rider_location_updates`: rider ID, approximate coordinates, recorded_at; use retention/aggregation policy. Prefer a separate time-series service only at scale.
- `outbox_events`: `id`, aggregate type/ID, event type, JSON payload, status, attempts, available_at, locked_until, processed_at, last_error_code, created_at. Avoid tokens and payment secrets in payload.
- `audit_logs`: actor ID/type, action, resource type/ID, reason, request ID, safe metadata, timestamp. Restrict update/delete permissions.

## 3. Critical indexes and constraints

- Unique normalized email and phone (partial unique indexes, allow nullable only if the product permits it).
- `restaurants(status, zone_id)` / catalog availability and menu indexes; `menu_items(restaurant_id, is_available)`.
- `orders(customer_id, created_at desc)`, `orders(restaurant_id, status, created_at)`, `orders(status, created_at)` for worker/admin queues.
- `order_items(order_id)`, `order_events(order_id, created_at)`.
- `payment_attempts(order_id, created_at desc)` and unique provider event ID.
- `outbox_events(status, available_at, created_at)` for claim loops.
- Unique idempotency keys scoped to caller/action; check constraints for positive quantity, non-negative money and legal enums.
- Geo queries: enable PostGIS only if nearby filtering needs it; otherwise calculate simple service-area filtering initially. Do not use distance calculation as the sole serviceability rule.

## 4. State values

- Order: `pending_payment`, `placed`, `accepted`, `preparing`, `ready_for_pickup`, `picked_up`, `delivered`, `cancelled`, `rejected`.
- Payment: `not_required`, `pending`, `succeeded`, `failed`, `unknown`, `partially_refunded`, `refunded`.
- Delivery job: `unassigned`, `assigned`, `accepted`, `arrived_at_pickup`, `picked_up`, `arrived_at_dropoff`, `delivered`, `failed`, `cancelled`.

Keep order state and payment state separate. Not every failed payment means an order can be discarded immediately; it depends on payment method/provider certainty and business rules.

## 5. RLS and access model

Preferred MVP path: only backend services connect to the database; mobile clients do not issue direct Data API queries. Backend authorization remains mandatory. Use non-owner database roles with explicit grants where possible; schema/table permissions should reflect write ownership. RLS is defense in depth, not a substitute for backend checks.

If direct Supabase Data API access is enabled later:

1. Verify the chosen custom/third-party JWT integration is supported and configured.
2. Confirm claims and `auth.uid()` behavior using real signed tokens and tests.
3. Enable RLS on every exposed table, default deny, and write policies for each action.
4. Never expose `service_role`/secret keys. Supabase documents that secret keys can bypass RLS: https://supabase.com/docs/guides/database/postgres/row-level-security
5. Verify cross-customer orders, merchant ownership, rider assignment and admin privileges with automated negative tests.

## 6. Migrations and seed data

- `supabase/migrations/<timestamp>_description.sql` is the source of truth; commit schema changes and review them.
- Each migration should be repeatable in CI on a clean database, have constraints/indexes, and include rollback notes even if rollback means a forward fix.
- Separate dev, staging and production projects. Never test migrations on production first.
- Use deterministic fake restaurants/items/users in local seed files. Do not include real customer data, secrets or production database dumps.
- Before risky DDL, estimate lock impact and use staged expansion/backfill/contract changes.

## 7. Backup/restore

Confirm the Supabase plan's backup/PITR features and retention instead of assuming them. Maintain an export/backup strategy appropriate to the plan, encrypt backups, restrict access and test restore into a separate project at least quarterly and before major releases. A backup is only useful after a successful restore test.

## 8. SQL starter migration example

```sql
create extension if not exists pgcrypto;

create table if not exists public.users (
  id uuid primary key default gen_random_uuid(),
  display_name text not null check (length(display_name) between 1 and 120),
  email_normalized text,
  phone_normalized text,
  password_hash text,
  status text not null default 'active'
    check (status in ('active', 'locked', 'disabled', 'pending_verification')),
  email_verified_at timestamptz,
  phone_verified_at timestamptz,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),
  check (email_normalized is not null or phone_normalized is not null)
);
create unique index if not exists users_email_unique
  on public.users(email_normalized) where email_normalized is not null;
create unique index if not exists users_phone_unique
  on public.users(phone_normalized) where phone_normalized is not null;

create table if not exists public.auth_sessions (
  id uuid primary key default gen_random_uuid(),
  user_id uuid not null references public.users(id) on delete cascade,
  refresh_token_hash text not null unique,
  token_family_id uuid not null,
  expires_at timestamptz not null,
  rotated_at timestamptz,
  revoked_at timestamptz,
  created_at timestamptz not null default now(),
  last_used_at timestamptz
);
create index if not exists auth_sessions_user_active_idx
  on public.auth_sessions(user_id, expires_at) where revoked_at is null;
```

This is a starting example, not the complete production schema. Extend it via migrations and add explicit grants/policies appropriate for the chosen connection model.
