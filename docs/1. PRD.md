# Product Requirements Document (PRD)

**Product:** Food Delivery App  
**Status:** Draft v1.0 — assumptions must be confirmed  
**Primary market assumption:** Bangladesh; BDT currency, Asia/Dhaka timezone, Bangla + English UX.  
**Platforms:** Customer mobile app in Flutter first; merchant, rider and admin interfaces can be responsive web or separate apps later.

## 1. Vision

Let customers discover nearby restaurants, order food with transparent pricing, pay using supported local methods or cash on delivery, and follow the order through delivery. Restaurants manage menus and order preparation. Riders receive and complete delivery jobs. Admins manage trust, support and operations.

## 2. Roles

- **Customer:** browse, search, maintain addresses, cart, place/pay for orders, cancel only under allowed rules, track, rate and contact support.
- **Merchant owner/staff:** manage restaurant profile, availability, menu, item availability, accept/reject orders, update preparation status and view settlement summaries.
- **Rider:** go online/offline, accept assigned jobs, update pickup/delivery status, share location only while working and view delivery history.
- **Support/admin:** review users/restaurants/riders, handle disputes/refunds, inspect audit trails and configure service areas. Privileged actions require stronger access controls.
- **System worker:** payment webhook processor, notifications, dispatch worker and scheduled cleanup jobs. Never a user-facing role.

## 3. MVP scope

1. Email/phone-based registration and login through our own Auth API (not Supabase Auth).
2. Access-token verification, refresh-token rotation, logout, password reset and verified contact flow.
3. Customer profile and multiple delivery addresses.
4. Restaurant listing filtered by service area/open status; categories, search and restaurant details.
5. Menus, options/add-ons if needed, item availability and cart validation.
6. Checkout with delivery address, fee/tax/discount breakdown and idempotent order creation.
7. COD and one online payment provider selected after merchant-account approval; never store card credentials.
8. Merchant order acceptance and food preparation status.
9. Rider assignment (MVP may start with manual/admin assignment), pickup, en-route and delivered statuses.
10. Push/in-app status notifications, order history, basic support and admin audit log.
11. Operational metrics, backups, automated tests, staged deployments and incident runbooks.

## 4. Not in MVP (unless required by launch partner)

- Multi-country/multi-currency, complex loyalty, subscriptions, advanced recommendations, multi-restaurant cart, real-time route optimization, split tenders, wallet/credits, chat, AI-based dispatch and multi-region active-active deployment.
- MCP is a developer/tool integration only; it is not involved in customer orders or payment processing.

## 5. User stories and acceptance criteria

| Story | Acceptance criteria |
|---|---|
| Customer signs in | Incorrect credentials return generic errors; rate limits apply; password is never stored as plaintext; refresh token can be rotated/revoked. |
| Browse restaurants | Results are paginated, honor service area/open status, and show clear loading/empty/error states. |
| Add menu item | Server revalidates item availability and current price at checkout; client price is never trusted. |
| Place order | One client retry with the same `Idempotency-Key` creates at most one order/payment intent. Totals are calculated server-side. |
| Pay online | Payment status is confirmed through a verified provider webhook/server-to-server check, not merely the app redirect. |
| Track delivery | Only the customer, assigned rider, restaurant staff with access, and authorized support can see permitted status/location details. |
| Merchant updates order | Invalid state transitions are rejected and every change is recorded in `order_events`. |
| Admin performs refund | Permission is checked server-side, reason is required, audit record is written and provider result is reconciled. |

## 6. Non-functional requirements (initial targets)

These are launch targets, not claims of measured performance.

- **Availability:** target 99.5% monthly for MVP, excluding provider outages and announced maintenance.
- **Latency:** p95 read API under 500 ms and normal order submission under 1 s excluding payment-provider latency, measured in staging/production.
- **Correctness:** no duplicate orders under client retries; no negative/incorrect totals; durable event/audit history for order/payment transitions.
- **Security:** HTTPS only, least privilege, input validation, account enumeration resistance, rate limits, secure secrets, dependency scanning and tested recovery flows.
- **Accessibility/localization:** responsive layouts, readable contrast, screen-reader labels, Bangla/English strings and BDT formatting.
- **Observability:** correlation/request ID, structured logs without passwords/tokens/payment secrets, service health metrics and actionable alerts.

## 7. Product decisions to confirm

1. First launch city/service zones, delivery radius and minimum order.
2. Phone OTP, email link, or email+password for sign-in. Do not send real OTPs until an SMS/email provider and budget are agreed.
3. Online payment provider(s), COD availability, refund/settlement procedures and provider merchant-account readiness.
4. Rider model: own fleet, restaurant delivery, or third-party courier.
5. Whether customers may cancel after restaurant acceptance and how refunds work.
6. Restaurant commission, delivery fee, VAT/tax rules and discount ownership. Confirm legal/accounting rules locally.
7. Merchant/admin dashboard platform and who has access to production data.

## 8. Success metrics

Track funnel and operations: signup completion, restaurant-view-to-cart rate, checkout conversion, order acceptance time, preparation time, delivery time, cancellation rate, payment failure rate, refund rate, repeat orders, support contacts per 100 orders and order complaint rate. Add privacy-conscious analytics and retention limits.

## 9. Risks

- Two backend languages increase staffing, CI, debugging and operational cost. Keep Go as the core API and use Rust for a narrow dispatch/optimization worker where beneficial.
- Custom authentication is security-sensitive and must be reviewed before public launch.
- Payment webhooks may be delayed/duplicated; processing must be idempotent and reconciled.
- Food availability, delivery distance, fees and order state must be validated on the server.
- Poor rider GPS coverage and provider downtime require a polling/manual fallback.

## 10. MVP exit criteria

A staged pilot is acceptable only when all critical end-to-end journeys pass, payment and webhook reconciliation are tested in sandbox, authorization tests show no cross-user access, order/payment state transitions are enforced, backup restore has been rehearsed, alerts are active, and support/admin operators have a documented runbook.
