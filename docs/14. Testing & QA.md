# Testing & Quality Assurance

## 1. Test pyramid

- **Unit:** domain rules, fee calculations, role checks, token claims validation, state machine and dispatch scoring.
- **Integration:** Go/Rust ↔ PostgreSQL, transaction rollback, migrations, outbox locks, provider adapters with fixtures, JWT verification across Go/Rust.
- **Contract:** OpenAPI validation, consumer/API schemas, webhook payload/signature fixtures.
- **End-to-end:** Flutter through staging API using seeded test accounts; order → merchant acceptance → payment confirmation → dispatch → delivery.
- **Security/performance:** authorization matrix, rate limit, dependency scan, load test and database pool exhaustion test.

## 2. Minimum high-value scenarios

### Authentication

- Valid registration/login and contact verification; invalid/expired challenge; incorrect password.
- Generic forgotten-password response for existing/non-existing account.
- Expired access JWT; wrong issuer/audience/key/algorithm; disabled user; rotated/reused refresh token; logout-all.
- Rate limit on login, OTP, resend and reset. Concurrent refresh requests from same device.

### Catalog and account scope

- Customer cannot edit another customer's address or view their order.
- Merchant A cannot modify Merchant B's restaurant/menu/order.
- Rider can only accept/advance assigned delivery job.
- Non-admin cannot invoke admin/refund actions; client-supplied role/status fields rejected.

### Money/order correctness

- Item price changes between cart and checkout; unavailable item; item from a second restaurant; quantity=0/negative/too large.
- Fee/tax/discount rounding boundaries; price integer overflow; currency mismatch.
- Simultaneous requests with same idempotency key create one order.
- Same key with changed body returns `409`.
- Illegal status transition rejected; append-only events created.
- DB failure rolls back order/order_items/outbox together.

### Payments

- Valid, invalid and replayed webhook; duplicated/out-of-order provider events; timeout with unknown provider status; refund duplication.
- App redirect says success but webhook/status says pending/failed.
- Provider is down after order creation; reconciliation succeeds after recovery.

### Dispatch/delivery

- Rust worker crashes after claiming job; lease expires and retries.
- Duplicate dispatch proposal; rider becomes unavailable between scoring and commit.
- Location update from non-assigned rider; stale/too-frequent location; worker backlog.
- Manual assignment fallback works.

### Flutter

- Loading, empty, no network, retry, 401 refresh, 403, 409, 429, server unavailable and expired quote states.
- Double tap Place Order; app killed/restarted during pending payment; deep link returns without verified payment.
- Small display sizes, keyboard overlap, large font, screen reader labels, localization/Bangla text rendering.

## 3. Suggested CI commands

```bash
# Flutter
cd apps/customer_flutter
 dart format --set-exit-if-changed .
 flutter analyze
 flutter test

# Go
cd services/api-go
gofmt -w .
go vet ./...
go test -race ./...

# Rust
cd services/dispatch-rust
cargo fmt --check
cargo clippy --all-targets --all-features -- -D warnings
cargo test
```

CI should use a disposable database to apply all migrations from empty state and run integration tests. Keep test credentials isolated; never allow a test job to target production.

## 4. Test data strategy

- Use synthetic customers/restaurants/riders and fake provider responses.
- Do not copy production PII into dev/staging. If sanitized real-like data is needed, generate it with a documented anonymization procedure.
- Keep deterministic clock/UUID/provider fixtures for state and webhook tests.
- Reset only disposable test environments.

## 5. Quality gates

- No failing lint/unit/integration/contract tests.
- Every API endpoint has auth policy and object-level negative tests if protected.
- Every payment/order mutation has concurrency/idempotency coverage.
- New migrations work on empty DB and supported prior schema; risky migration reviewed.
- Critical user journeys have an automated or documented manual test.
- No high-severity secrets/dependency scan findings without approved mitigation.

## 6. Performance test plan

Establish baseline before optimization. Load test catalog reads, login, quote/order write and tracking separately. Monitor p50/p95/p99 latency, error rate, DB connections, slow queries, row-lock contention, outbox age and provider latency. Use realistic datasets and avoid load tests against shared production services without approval.

## 7. Release checklist

- [ ] Staging migration applied and reviewed.
- [ ] Smoke tests passed on supported Android devices; iOS if in scope.
- [ ] Payment sandbox and signed webhook test passed.
- [ ] Backup/restore or recovery expectations confirmed for the current Supabase plan.
- [ ] Alerts for error rate, pending payment, outbox backlog and DB connections are active.
- [ ] Rollback/forward-fix and incident contact documented.
- [ ] Store listing/privacy disclosures, support process and operational staffing ready.
