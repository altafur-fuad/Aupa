# System Architecture

## 1. Decisions and rationale

**Recommended initial shape:** a modular Go public API plus background integration workers, a private Rust dispatch/optimization worker, and one Supabase-managed PostgreSQL database. This satisfies the planned Rust + Go stack without creating a large fleet of tiny microservices. If the Rust component has no meaningful job yet, delay deploying it rather than adding an empty service just to use a language.

Go owns request orchestration, custom authentication, profiles, catalog, cart validation, checkout orchestration, merchant/admin APIs, payment-provider adapters and notification jobs. Rust owns a bounded dispatch/assignment calculation (candidate scoring, distance/time heuristics, assignment suggestions) and consumes durable work records. Keep final authorization and status transition policy in trusted backend code; Rust output is a proposal, not an instruction that bypasses business rules.

## 2. Logical topology

```text
Flutter Customer App / Merchant-Rider UI
                 |
               HTTPS
                 v
          Go API (public)
      / auth / catalog / cart \
     / checkout / operations   \
                 |
       Supabase Postgres (TLS)
          |          |
   durable outbox    order/payment data
          |
      Rust worker (private)
    dispatch scoring / assignment proposal
          |
      validated result -> Go domain handler

Go workers -> payment, SMS/email, push, maps/geocoding providers
Provider webhooks -> Go webhook endpoints -> idempotent DB transaction
```

A message queue is not mandatory on day one: `outbox_events` can act as a durable work queue using row locks and retry metadata. Add a queue when backlog volume/throughput warrants it. The Rust worker can run as a separate container and claim only `dispatch.requested` records. Do not let it mutate arbitrary customer/auth/payment tables.

## 3. Service boundaries

### Go public API / core backend

- REST `/v1`, validation, authentication/authorization middleware, rate limiting.
- User identity, sessions, addresses, restaurant/menu CRUD, cart/checkout validation, order API orchestration and merchant/rider/admin operations.
- Payment intent creation, webhook signature verification, reconciliation, notifications, outbox dispatch and operational endpoints.
- Uses transactions for order creation and status changes. Amounts/prices are server-authoritative.

### Rust private worker

- Consumes validated dispatch work; calculates eligible riders based on zones, availability, order size and distance/time estimates.
- Emits an assignment proposal with algorithm version, candidate scores and reason codes; Go validates rider availability, access and current order state before committing assignment.
- No public internet endpoint required in MVP. Use DB worker role or authenticated private HTTP; pick one access path and document it. Prefer a narrowly privileged DB role and lease/claim protocol if polling the database.

### Supabase/Postgres

- System of record for users, sessions, catalog, order/payment records, state history and outbox.
- Schema migrations tracked in Git, applied through controlled release jobs.
- API services should normally connect through PostgreSQL using a backend-only credential and TLS. If any client accesses Supabase Data API directly, RLS must be correctly designed for the exact JWT trust model.

## 4. Important custom-auth and RLS limitation

A custom Go-issued JWT is not automatically a Supabase Auth identity. `auth.uid()` relies on claims/token context that Supabase recognizes. Supabase supports configured custom/third-party JWT approaches, but this requires explicit configuration and compatible claims/keys: https://supabase.com/docs/guides/auth/jwts

**MVP recommendation:** Flutter calls only the Go API. Go/Rust connect to Postgres server-side with secrets and enforce identity/authorization in backend code. Do not put a Supabase database password, secret/service key or backend token in the app. Because backend DB credentials can bypass RLS, use the narrowest DB roles, least privilege, parameterized SQL and explicit owner checks. Enable RLS as defense in depth, but do not pretend RLS protects calls that use a privileged server credential.

If direct Flutter-to-Supabase Data API access is later required, formally design a supported external JWT trust configuration, test `auth.uid()`/claims and policies with real tokens, and ensure publishable keys only are shipped. Do not mix custom bearer tokens with Supabase session assumptions.

## 5. Request and event flow

**Place order:** Go authenticates user → validates body and idempotency key → starts DB transaction → reads fresh menu/availability and address/service area → calculates item snapshots, taxes/fees/discounts → inserts order and items → inserts `order.created` outbox event → commits → returns order ID/status. Payment intent follows according to chosen payment flow. Repeated idempotency key returns the original compatible result.

**Payment webhook:** Go verifies provider signature and timestamp → stores webhook/event ID under unique constraint → resolves payment/order → applies allowed transition in a transaction → records payment/order event → commits → queues notification. Duplicate webhook is a no-op. The browser/app redirect is informational only.

**Dispatch:** outbox worker leases dispatch event → Rust calculates candidates → outputs proposal → Go validates proposal against current order/rider state → assignment and event committed transactionally. Failed jobs retry with backoff and dead-letter state.

## 6. Data ownership and transaction rules

Use one Postgres database for operational simplicity, but make ownership explicit: Go owns writes to `identity.*`, `catalog.*`, `commerce.*`, `payments.*` and `ops.*`; Rust reads minimum required views and writes only dispatch proposal/job results through a restricted interface/role. Do not permit both languages to independently invent order transitions. Keep transactions short; never call payment provider or send email while holding a database transaction open.

## 7. Cross-cutting controls

- HTTPS/TLS, trusted reverse proxy, request size and timeout limits.
- JWT signature, allowed algorithm, issuer, audience, expiry and key ID validation.
- Central request ID and trace context; structured logs with redaction.
- Rate limiting for login, OTP, password reset, checkout and webhooks.
- Idempotency for checkout, payment intent creation and webhook processing.
- Strict CORS only if web clients exist; CORS is not authentication.
- Database backups, restore drills, migration rollback/forward strategy, secrets rotation and dependency scanning.

## 8. Scale path

1. Start with Go API + Postgres + one Rust worker container; use a managed container platform and Supabase.
2. Add separate notification/settlement workers only when operationally useful.
3. Add a queue (managed queue or Redis-backed broker) if outbox polling latency/backlog needs it.
4. Partition/archive large `order_events`/location history after measuring growth.
5. Add caching/read replicas only from evidence; never cache authorization decisions or mutable prices unsafely.
6. Split services only when independent ownership, scaling or team boundaries justify distributed-system costs.

## 9. Failure modes and mitigations

| Failure | Mitigation |
|---|---|
| Payment provider times out | Mark payment attempt unknown/pending; query provider/reconcile; do not issue duplicate charge blindly. |
| Worker crashes | Lease expiration, retries, bounded backoff, dead-letter alerts. |
| Database unavailable | Fail writes safely; no fake success; health/readiness checks and retry policy. |
| Duplicate request/webhook | Unique idempotency/event key and transaction. |
| Rust proposal is stale | Go rechecks order status/rider availability in transaction before committing. |
| Notification provider fails | Durable retry; order state remains correct even if notification is delayed. |
