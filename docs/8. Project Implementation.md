# Project Implementation Roadmap

## Principle
Ship a narrow, correct end-to-end journey before building every dashboard. Since the Flutter UI already exists, map these tasks to current screens/components and avoid a visual rewrite unless usability testing identifies a problem.

## Phase 0 — Repo audit and decisions (1–3 days)

- Inventory current Flutter routes/screens, package versions, state management, API assumptions and reusable design components.
- Confirm target city/zone, login method, rider model, cancellation policy, payment provider, fees/tax and launch roles.
- Create dev/staging/prod environment plan and secret inventory.
- Decide exact Go/Rust ownership; Rust must own a narrow dispatch calculation/job, not duplicate Go order policy.

**Exit criteria:** architecture decisions are recorded, UI-to-feature map exists, every external dependency has an owner and dev/test credentials plan.

## Phase 1 — Foundation (3–5 days)

- Repo layout, formatting, linting, environment config, Docker Compose/local stack, health endpoints and CI pipeline.
- Supabase local/dev project, migrations and fake seed data.
- Request IDs, JSON logs/redaction, API error model, OpenAPI file and DB connection pool/timeouts.
- Flutter API client/repository conventions, navigation, localization, reusable loading/error/empty states.

**Exit criteria:** clean checkout of repo can run documented checks; migration runs from empty DB; secrets absent from Git.

## Phase 2 — Identity and account security (4–7 days)

- Register/login/contact verification, password reset, refresh rotation/reuse detection, logout and profile endpoint.
- Use Argon2id (or reviewed alternative) for password hashes; use opaque refresh tokens stored hashed in DB.
- Secure token storage on iOS/Android, auth interceptor and refresh race coordination in Flutter.
- Role and scope model, rate limits, audit logs, brute-force and account-enumeration tests.

**Exit criteria:** expired/revoked tokens fail; concurrent refresh is safe; cross-user negative tests pass; reset/verification tokens are one-use.

## Phase 3 — Catalog and address flow (4–6 days)

- Restaurant CRUD and review/moderation state, opening hours/serviceability, menu categories/items/options, image storage.
- Restaurant browsing/search, menu details and customer addresses.
- Merchant ownership checks and public-vs-private field allowlists.

**Exit criteria:** user sees only active/serviceable catalog; merchant cannot edit another restaurant; menu availability changes propagate to checkout validation.

## Phase 4 — Cart, pricing and orders (5–8 days)

- Cart UX and `/checkout/quote`; server totals; currency minor units; address snapshot; idempotent create order.
- Order/order-item snapshots, state transition validator, `order_events`, cancellation rules and merchant acceptance/preparation flow.
- Transactional outbox for notifications and dispatch requests.

**Exit criteria:** duplicate submissions produce one order; menu price changes are rechecked; failed transaction leaves no partial order; illegal status jump rejected.

## Phase 5 — Payment (provider-dependent, 4–10+ days)

- Select provider after checking merchant onboarding, supported methods, settlement/refunds, sandbox and webhook docs.
- Payment attempt creation, provider idempotency, signature verification, dedupe table, reconciliation job and refunds.
- COD path if business decision allows.

**Exit criteria:** delayed/duplicated/out-of-order webhook tests pass; redirects alone cannot set payment success; support can inspect pending/unknown cases.

## Phase 6 — Delivery and Rust worker (4–8 days)

- Admin/manual rider assignment first; rider availability, pickup and delivery transitions.
- Rust worker consumes dispatch jobs and proposes eligible riders; Go revalidates and commits assignment.
- Tracking via periodic location updates or status polling, with update timestamp and privacy/retention policy.

**Exit criteria:** stale dispatch proposal cannot assign an unavailable rider; failed worker retries; only permitted roles see tracking; manual fallback works.

## Phase 7 — Notifications, support and admin (3–6 days)

- Push/email/SMS provider adapters, durable retries, templates/localization and delivery status.
- Admin/support screens for user/restaurant status, order timeline, payment reconciliation and refund request.
- Audit events for high-risk actions.

**Exit criteria:** notification failure does not change order truth; privileged actions are role/scope checked and audited.

## Phase 8 — Hardening and pilot (5–10 days)

- Threat model, dependency/image scans, API authorization matrix, load tests, accessibility pass, backup restore, data-retention review and support playbook.
- Test in sandbox; pilot with limited restaurants/riders; alerts on payment discrepancies, dispatch backlog, API errors and database connection exhaustion.
- Progressive rollout and rollback procedure.

**Exit criteria:** all critical journeys pass, no open critical/high security findings, operational owner is on call and restore has been proven.

## Suggested initial repository layout

```text
apps/customer_flutter/
services/api-go/
services/dispatch-rust/
api/openapi.yaml
supabase/config.toml
supabase/migrations/
supabase/seed.sql
infra/docker/
infra/ci/
docs/
```

## Prioritization rule

P0: data access, account security, money/order correctness, idempotency, backup/restore. P1: full tracking, push polish, analytics dashboards. P2: AI recommendations, loyalty, advanced optimization, multi-region and unnecessary microservices.
