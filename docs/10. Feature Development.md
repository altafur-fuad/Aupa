# Feature Development Workflow

## Definition of ready

Before implementation, a feature has user story, acceptance criteria, endpoint/data impact, permission matrix, error states, localization needs and observability requirements. Payment/order/security changes need a brief threat/failure review.

## Standard workflow

1. **Inspect existing UI and code.** Reuse the partially completed Flutter UI. Identify current route, state controller, model and API seams.
2. **Specify API and state transitions.** Update `api/openapi.yaml` and `docs/5. API.md` before wiring UI to an undocumented response.
3. **Design data migration.** Add migration with constraints/indexes, safe upgrade path and seed changes. Review query/lock impact.
4. **Implement domain first.** Write domain/use-case logic and unit tests; keep controllers thin. Go owns application/order policy; Rust returns dispatch recommendations only.
5. **Implement API and authorization.** Check actor role + resource scope on every object. Validate unknown fields rather than mass-assigning structs.
6. **Connect Flutter.** Service → repository → view model/state controller → view. Model loading, empty, offline, validation, unauthorized and retry states.
7. **Add telemetry.** Request ID, business event, latency/error counters and safe logs. Avoid phone/email full values, tokens, OTPs or provider payload secrets.
8. **Run tests and review.** Use the relevant commands in `6. AGENTS.md`. Add negative tests and retry tests for mutations.
9. **Release gradually.** Behind a feature flag when appropriate; migrate backwards-compatibly; watch metrics; document rollback/forward fix.

## Feature-specific requirements

### Authentication

- Normalize email/phone; verification and recovery challenges have expiry, attempt limits and one-use consumption.
- Use Argon2id or documented secure alternative for passwords; never SHA-256 alone.
- Rotate refresh token on use; detect reuse, revoke family and create a security audit event.
- Test multi-device logout, disabled accounts, expired tokens, clock skew and concurrent refresh.

### Catalog/menu

- Enforce merchant's restaurant scope on writes.
- Public listing exposes only approved active restaurants/items.
- Price and availability changes are rechecked at checkout; cache expiry is explicit.
- Image upload goes through a controlled signed upload or backend validation; do not allow arbitrary remote URLs to create SSRF/image-fetch risk.

### Cart/checkout/orders

- One order = one restaurant for MVP.
- Validate item belongs to restaurant; quantity bounds; add-ons; service area; address ownership; minimum order; delivery fee; promotion rules; current prices.
- Persist price/name/options snapshots in the same transaction as order items.
- Use idempotency; state transitions are server-controlled and append to `order_events`.
- Do not hold DB transactions open during payment/network calls.

### Payments/refunds

- Verify webhook authenticity according to the provider's current docs, dedupe provider event ID and reconcile uncertain statuses.
- Never store card PAN/CVV. Use provider-hosted/approved payment collection flow.
- Refund endpoint requires privileged role, scope, amount bounds and reason. Keep a full audit trail.

### Rider tracking

- Collect location only while online/on an active delivery as disclosed.
- Check assigned rider/order relation on every update; cap update frequency and payload size.
- Show location freshness; expire old location data under policy. Do not expose exact rider location to unrelated users.

## Pull request template

```markdown
## What changed
## User/business behavior
## API/schema changes
## Authorization and threat considerations
## Tests run (include commands)
## Migration/release/rollback notes
## Observability and alerts
## Screenshots or recordings (UI changes)
```

## Acceptance gates

A feature is done only if acceptance criteria pass, API/schema docs match code, tests cover expected and forbidden behavior, strings are localizable, secrets/logging are reviewed, and operational handling of failures is known.
